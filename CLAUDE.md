# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FertiLedger ERP (package `fertiledger-erp`, repo name `agrisynq-erp`): an Indian agri-inputs trading ERP (fertilisers, pesticides, seeds) covering master data, purchases, sales, inventory/batches, logistics, accounting, GST, bank reconciliation, reports and admin. Domain concepts that recur everywhere: batch/expiry tracking, licences, farmer sales for the FMS/iFMS government portal, C&F (carrying & forwarding) stock, memo (unbilled) purchases/sales, GSTIN/HSN/CGST-SGST-IGST.

Stack: Next.js 14 App Router, React 18, TypeScript, Tailwind, Supabase (Postgres + Auth + RLS) via `@supabase/ssr`, zod, sonner, lucide-react, Vitest.

## Commands

```
npm run dev            # next dev
npm run build
npm run lint           # next lint
npm run type-check     # tsc --noEmit
npm test               # vitest run (all)
npx vitest run src/lib/__tests__/phase1.test.ts          # single file
npx vitest run -t "test name pattern"                    # single test
bash supabase/tests/run_db_tests.sh                       # DB: applies ALL migrations to a throwaway Docker Postgres + runs the SQL e2e tests
```

`run_db_tests.sh` starts/creates the `fl-pg` container itself (needs Docker Desktop running) and uses a Supabase stub (`supabase_stub.sql`) and a disposable `fl-pg` container; it never touches a real project. Run it after ANY change to `supabase/migrations/*` or to posting logic - migrations 031-034 were once committed that could not even apply, and nothing caught it. Add new scenarios as `supabase/tests/e2e_*.sql` (see `e2e_posting.sql` for the pattern: act as a user via `SET ROLE authenticated` + `request.jwt.claim.sub`).

**Running the real app locally (no cloud project needed):** `bash supabase/local/stack.sh up` starts a Supabase-compatible stack (Postgres 17 Supabase image, GoTrue auth, PostgREST, Kong) from the public Supabase images on ports 55321 (API) / 55322 (Postgres) - separate from any other Supabase project - applies ALL migrations as the non-superuser `postgres` role (like the hosted service) and writes `.env.development.local` (git-ignored; overrides `.env.local` in `next dev`, so your real keys are untouched). `stack.sh seed` creates a demo company with one login per role (`admin@ branch@ accountant@ sales@ stock@ fms@ viewer@ fertiledger.test`, password `Passw0rd#Local`); `stack.sh apply <file.sql>` applies a new migration to the running DB; `stack.sh reset` wipes it. On top of that: `node scripts/smoke-pages.mjs` logs in and requests EVERY dashboard page (catches crashes / bad queries on load), and `npm run test:int` runs the real server actions as real users against the stack (`src/**/*.int.test.ts`; `read-actions` calls every `get*` action and fails on thrown OR swallowed errors, `money-chain` drives purchase -> sale -> receipt -> credit note). These found bugs the SQL tests could not (missing foreign keys, ambiguous PostgREST embeds, wrong enum values, a non-existent column in an insert): run them after changing actions or schema. PostgREST gotchas learned: a relationship needs a real foreign key; when a table has TWO foreign keys to the same table you must name one (`parties!sales_invoices_customer_id_fkey(name)`); views cannot be embedded.

Env (`.env.local`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SECRET_KEY`, etc. The dashboard home page checks these to decide whether Supabase is "configured".

The `run-phaseN-push.bat/.ps1` scripts at the root are the previous author's release ritual: `tsc --noEmit` → `vitest run` → `git add -A` → commit → `git push upstream main`. Commit messages follow `feat(phaseN): … TS:CLEAN Vitest:PASS`. Note they `git add -A` and push to the `upstream` remote (`caprivaa14/agrisynq-erp`), not `origin`; don't run them blindly.

## Architecture

**Request flow:** `src/middleware.ts` → `lib/supabase/middleware.ts#updateSession` refreshes the session and enforces auth. `app/(auth)/login` is public; everything under `app/(dashboard)` is wrapped by a layout (Sidebar + Topbar) that re-checks `supabase.auth.getUser()`. Path alias `@/*` → `src/*`.

**Page pattern (follow it for new modules):** `app/(dashboard)/<module>/<feature>/page.tsx` is a thin server component that calls server actions to fetch initial data, then renders a `*Client.tsx` component (forms, tables, filters, `sonner` toasts) with that data as props. Business logic lives in server actions, not in client components.

**Server actions (`src/actions/*.ts`, `"use server"`)** are the entire backend API — there are no route handlers. Conventions:
- Every action starts with `getUserContext()` (`actions/context.ts`), which resolves `tenantId / organisationId / branchId / roleName` from `user_roles` for the session user. Never accept tenant/org IDs from the browser; scope every query with them.
- `getUserContext` has a deliberate fallback: if the user has no `user_roles` row (migrations not applied / unprovisioned user) it returns the auth user id as placeholder tenant/org so pages render empty rather than loop. Be aware this masks missing-role problems.
- Input is validated with zod schemas defined at the top of each action file; mutations call `writeAuditLog()` (best-effort, never throws) and `revalidatePath()`.
- Document numbers come from Postgres RPCs (`generate_po_number`, `generate_invoice_number`, `generate_pi_number`, `generate_so_number`, `generate_sq_number`, `generate_cn_number`, `generate_fs_number`); stock via `get_stock_balance`, `get_expiring_batches`. Reports/GST/bank/admin read from SQL views (`vw_*`) built in the later migrations.
- **Posting is done in the database, atomically** (migration 038): `post_sales_invoice`, `post_purchase_invoice`, `post_credit_note` (`SECURITY DEFINER`, tenant from session) validate stock/batches, write `stock_ledger`, create a balanced journal voucher (perpetual inventory: purchase DR Stock/ITC CR Creditors; sale DR Debtors CR Sales/GST + DR COGS CR Stock at batch cost) and flip the status in one transaction. Receipts post via `rpc_post_payment_receipt` (037), adjustments via `post_stock_adjustment` (032). Server actions just call these RPCs; do NOT reimplement posting in TypeScript, and do not insert POSTED rows directly.
- **Role permissions are enforced in the database (migration 049):** `has_permission(module, action)` reads the `role_permissions` matrix; `require_permission()` is patched into the top of every posting/approval function (23 of them; `e2e_permissions.sql` asserts the count); a `a_readonly_guard` trigger on EVERY table with a `tenant_id` blocks users whose roles have only read/export permissions (viewers) from writing by any route. After adding a table with `tenant_id`, run `SELECT attach_readonly_guard();` (the permissions test fails otherwise). Calls with no signed-in user (migrations, service key) are never blocked. The default matrix was completed: BRANCH_ADMIN = SUPER_ADMIN minus user admin/period locks/audit/sensitive KYC; ACCOUNTANT can create+post purchases. Note per the matrix an ACCOUNTANT can NOT post sales invoices and `purchases.post`/`sales.post` are otherwise admin/sales-manager only - confirm this with the business before go-live and change `role_permissions` if needed.
- **Status lock-down (039):** RLS lets users create/edit only DRAFT documents; nothing but the posting functions can set POSTED. Posted documents/vouchers are immutable to users. The system chart of accounts (codes 1001,1010,1020,1040,2001,2005,2010-12,3001-03,3020,4001-03,4040-42,4050) must be seeded or posting raises a clear error.
- `batch_register.current_qty` is maintained by a trigger on `stock_ledger` (038) - never update it from code. Views over RLS tables use `security_invoker`.
- Invoice/GST arithmetic lives in `src/lib/gst.ts` (`computeLine`, `sumLines`, `splitGst`, `resolveInvoiceType`) and is shared by sales invoices, purchase invoices and credit notes. Rule: round each line to 2dp, document totals = sum of rounded lines, CGST+SGST always equals total GST. Don't re-implement GST math inside actions; it has real unit tests in `src/lib/__tests__/gst.test.ts`.

**Database (`supabase/migrations/001…035`)** is the source of truth for the schema and is applied manually/in order (no Supabase CLI config in the repo). `_v2` migrations (011–016) rework the earlier master-data tables; `009_rls_fix` patches RLS. Multi-tenancy is `tenant → organisation → branch/location`, enforced by RLS plus explicit filters in actions. Posting a purchase invoice is meant to create batches, stock-ledger movements and an AP entry (the GRN page is intentionally just an explainer for this). `src/lib/types.ts` holds shared hand-written types (no generated Supabase types).

**Navigation:** the sidebar (`components/layout/Sidebar.tsx`) hard-codes `NAV_GROUPS`; new pages must be added there manually.

Period locks live in `period_locks` (010) and are enforced by DB triggers (036).

- Lint is clean (0 errors; a few `react-hooks/exhaustive-deps` warnings remain in master-data slide-overs) and both lint and TypeScript errors now fail `next build`.
- FMS (migration 040, `actions/fms.ts`, tests in `supabase/tests/e2e_fms.sql`): farmer sales post atomically via `post_farmer_sale` (subsidised sales require a PoS transaction ID; PoS IDs are unique per tenant case/space-insensitively; journal books Subsidy Receivable account 1040); `fms/ledger` (compliance flags + CSV export) and `fms/reconciliation` (portal totals vs system, resolve with note) are implemented. `fms/reissue` (migration 041: `cancel_farmer_sale` / `reissue_farmer_sale` reverse stock + journal dated today, never reuse a PoS id, block cancelling once subsidy is claimed) is implemented. `fms/import` (migration 042 `import_fms_data`: matches an uploaded portal CSV to sales by PoS id and reports MATCHED / QTY_MISMATCH / SUBSIDY_MISMATCH / MISSING_IN_SYSTEM / CANCELLED_IN_SYSTEM / NOT_POSTED / DUPLICATE_IN_FILE / INVALID plus sales missing from the portal; CSV parsing and column mapping are in `src/lib/csv.ts` + `src/lib/fms-import.ts` with unit tests) is implemented. `fms/subsidy` (migration 043, `actions/subsidy.ts`, `e2e_subsidy.sql`) is implemented: claims are created/submitted/received/rejected/cancelled ONLY via SECURITY DEFINER functions (users have read-only access to `subsidy_claims`/`subsidy_receipts`); a receipt posts DR Bank / CR Subsidy Receivable (1040), partial receipts supported; claiming sales in a locked period is allowed (farmer_sales uses its own lock trigger `trg_enforce_period_lock_fs`) but booking the money is not. The FMS module is complete; invariants worth testing after changes: balance of account 1040 == unclaimed + claimed-unreceived subsidy.
- Placeholder "Coming in Phase N" pages (UI stubs, no actions/tables wired): `accounting/settlements` (`sales/delivery-challans` now redirects to `logistics/challans`). Schema for some (FMS, gate passes, challans: migrations 025/026/028) exists; the sidebar's "Delivery Challans" under Logistics (`logistics/challans`) is the implemented one.
- C&F (migration 044, `actions/cf.ts`, `e2e_cf.sql`): C&F stock is DERIVED from the ledger (`vw_cf_stock`: locations of type CF_DEPOT/THIRD_PARTY, agent = `locations.custodian_party_id`); the agent's counts are recorded with `record_cf_confirmation` (variances need a remark; every count is logged in `cf_stock_confirmations`; `cf_stock_register` is read-only to users). Transfers: users can only create/edit DRAFT transfers; `approve_stock_transfer` (C&F withdrawals need the company approval ref + request no), `rpc_dispatch_stock_transfer` (per product+batch availability, session-checked) and `receive_stock_transfer` (received / damaged / derived shortage, loss written off at cost to account 4050 Transit Loss) are the only way to move status. Shared UI: `components/logistics/TransferDialogs.tsx`. Gate passes (migration 045, `actions/gate-passes.ts`, `e2e_gate_pass.sql`): recorded & linked, NOT a dispatch blocker. `issue_gate_pass` derives the gate location from the document and only allows valid (document, pass type, status) combinations (transfer / sales invoice / purchase invoice / credit note / delivery challan); one active pass per document+type; passes are immutable, a wrong one is voided with a reason (`void_gate_pass`) and re-issued; vehicle/mobile are validated and normalised; `vw_gate_pass_pending` lists last-60-day movements with no pass. Users have read-only table access.
- **Schema trap:** `delivery_challans` is the 025 table (`challan_number`, `from_location`, `vehicle_number`, `eway_bill_number`, `narration`, purposes `challan_purpose`). Migration 028 also declares a `delivery_challans` with `CREATE TABLE IF NOT EXISTS` which was silently skipped, so 028's column names/enums (`challan_no`, `dispatch_location_id`, `*_enum`) do NOT exist; 046 added the missing compliance columns and repointed `transporter_id` to `transporters`. `actions/logistics.ts` maps real names to the names the challan screen uses. When a migration says `IF NOT EXISTS`, check the table really has those columns.
- **Memo purchases & stock journal** (migration 047, `actions/memo.ts`, `actions/stock-journals.ts`, `src/lib/memo.ts`, `e2e_memo.sql`): goods received before the supplier's invoice. `post_memo_purchase` brings stock in at COST = rate less percentage discount then flat discount, spread over paid+free units, NO GST (DR Stock 1020 / CR *Goods Received - Invoice Pending* 2005 per supplier; supplier challan/ref mandatory; every memo line starts its own batch). The supplier's invoice is posted normally AS BILLED, then `settle_memo_with_invoice` matches memo lines to invoice lines: clears 2005 at memo cost, takes the memo stock back out of the ledger for units still on hand, and for units ALREADY SOLD takes the invoice's stock out instead and books (invoice cost - memo cost) to COGS (so COGS ends at the true invoice cost). If the supplier billed a different product (A delivered, B billed) the UI offers a pre-filled **stock journal** (`post_stock_journal`: B out, A in; the outgoing VALUE is carried onto the incoming batch, no GL entry, incoming stock always a new batch). Never-billed goods: `close_memo_units` RETURN (stock back to supplier) or WAIVED (liability released to 3020). Pending-invoice reports: `vw_memo_pending`, `vw_memo_pending_by_supplier` (30-day highlight in the UI). Invariants tested: GL 2005 == sum of `vw_memo_pending.pending_value`; GL 1020 == stock sub-ledger (units x batch cost). Posting/matching/journals are limited to admin/accountant roles (memo receipt also stock manager) via `has_any_role`; all tables are read-only to users except DRAFT memos. New system account **2005**.
